## @module  [51cd0049]
Здесь из сырых суточных замеров скважины делаются числа, которые понимают модели. Один класс `FeatureBuilder` строит два представления одних и тех же дневных каналов:

- `sequence()` — матрица «дни × 20 каналов» для Transformer: соседние дни модель видит сама через внимание и свёртку;
- `tabular()` — «дни × 131 признак» для scikit-learn: у каждого дня своя строка, поэтому контекст (значения через ±1…14 дней и средние за неделю) приходится дописывать в строку явно.

Общая идея всех каналов — **относительные** величины: частота относительно рабочей частоты скважины, дебит относительно медианы за прошлые 30 дней, дебит относительно уровня «до скачка», нефть относительно базы «до подъёма» (там, где технолог ставит окончание). Так 50 Гц на одной скважине и 35 Гц на другой, 20 м³/сут и 400 м³/сут выглядят одинаково, и модели не нужны абсолютные числа (а их при ~120 обучающих скважинах не хватило бы для обобщения). Все нормировки считаются **внутри одной скважины** по её собственному ряду — утечки между скважинами нет.

Модуль не знает про разметку: `target()` и `training_mask()` живут в `WellSeries`. Выход ограничен диапазоном [-3; 3] (константа `CLIP`), пропуски заменены нулями.

## FeatureBuilder  [33686f33]
Класс без состояния: один экземпляр обслуживает все скважины, нечего «обучать» или сохранять. Константы класса — единственные настройки признаков:

| Константа | Значение | Смысл |
|-----------|----------|-------|
| `MIN_WORKING_FREQ` | 10 Гц | ниже этой частоты (или при `state` ≤ 0) насос считается остановленным |
| `MIN_STEP` | 0,1 Гц | минимальный подъём частоты, который считается «скачком» |
| `WINDOW` | 30 дней | окно «недавнего» уровня параметров |
| `BASE_DAYS` | 3 дня | сколько дней перед скачком (плюс сам день скачка) входит в базу нефти |
| `BELOW_RUN_CAP` | 14 дней | серия дней «нефть не выше базы», при которой `oil_days_below` достигает 1 |
| `SEQUENCE_CHANNELS` | 20 имён | порядок столбцов `sequence()`; сохраняется в весах `.pt` |
| `SHIFTED_CHANNELS` | 11 имён | каналы, которые для scikit-learn размножаются сдвигами и средними |
| `OFFSETS` | −14, −7, −3, −1, +1, +3, +7, +14 | сдвиги в днях |

**Почему порядок `SEQUENCE_CHANNELS` важен:** `TransformerSegmenter.save` записывает список каналов в файл весов, а `load` сверяет его с текущим; если канал добавили или переставили, старые веса дадут `ValueError` (иначе сеть молча получила бы данные «не в тех столбцах»).

Что означают 20 каналов (все безразмерные):

| Канал | Что это |
|-------|---------|
| `working` | 1, если насос работает (`state` > 0 и частота > 10 Гц) |
| `f_rel` | частота относительно медианной рабочей частоты скважины минус 1 |
| `f_diff` | суточное изменение `f_rel`, ×10 (подъём на 1 Гц при 50 Гц → 0,2) |
| `f_above_min30`, `f_below_max30` | насколько частота выше минимума / ниже максимума за 30 дней, ×10 |
| `liq_vs_30d`, `oil_vs_30d` | дебит жидкости / нефти относительно медианы за прошлые 30 дней |
| `wc_vs_30d` | обводнённость минус среднее за прошлые 30 дней, /10 |
| `pzab_vs_30d` | забойное давление относительно медианы за 30 дней |
| `days_since_step` | дней с последнего скачка частоты вверх, делённые на 120 (не больше 1) |
| `step_size` | размер последнего скачка относительно частоты до него, ×10 |
| `liq_vs_step`, `oil_vs_step`, `wc_vs_step` | дебит / обводнённость относительно уровня за день до скачка |
| `liq_missing` | 1, если в этот день нет замера дебита жидкости |
| `oil_vs_base` | нефть / база − 1, где база — медиана нефти за 3 дня до скачка и день скачка |
| `oil_below_base` | 1, если нефть не выше базы (нефть «вернулась» к уровню до подъёма) |
| `oil_days_below` | сколько дней подряд нефть не выше базы, /14, не больше 1 |
| `oil_drawdown` | просадка от максимума нефти после скачка, в долях базы |
| `oil_missing` | 1, если в этот день нет замера нефти |

Пять последних каналов добавлены в эксперименте с датой окончания: технологи ставят окончание там, где дебит нефти вернулся к уровню до подъёма. Результатов сравнения «до/после» пока нет.

### Пример
Синтетическая скважина из `tests/conftest.py` (`make_well()`: 120 дней, частота 48 → 50 Гц в день 40, дебит жидкости 100 → 110 с дня 42 на 30 дней):

```python
fb = FeatureBuilder()
well = make_well()
fb.sequence(well).shape        # (120, 20)
fb.tabular(well).shape         # (120, 131)
```

Реальная скважина 8822 (куст 615А, разметка: начало 30.07.2022, окончание 05.09.2022): 1587 дней ряда, из них `training_mask(45)` оставляет 128 дней, а `target()` отмечает 38 дней эффекта.

## FeatureBuilder.sequence_size  [f9749540]
Число каналов `sequence()`, то есть `len(SEQUENCE_CHANNELS)`. Передаётся в `TimeSeriesTransformer` как размер входа свёртки (`n_channels`), чтобы число не дублировалось в коде.

### Пример
```python
FeatureBuilder().sequence_size   # 20
```

## FeatureBuilder.tabular_names  [1d9c82cf]
Список из 131 имени столбцов `tabular()`. Нужен для отладки и разбора важности признаков.

Состав: 20 основных каналов + 11 каналов × 8 сдвигов (88, имена вида `liq_vs_30d@+7`) + 11 каналов × 2 средних (22, `..._mean_past7` и `..._mean_next7`) + 1 признак `f_diff_max_pm3` = 20 + 88 + 22 + 1 = 131.

> **Внимание, порядок имён не совпадает с порядком столбцов.** Список строится «канал за каналом» (`working@-14`, `working@-7`, …, `working@+14`, затем `f_diff@-14`, …), а `tabular()` кладёт блоки «сдвиг за сдвигом» (сначала все 11 каналов со сдвигом −14, потом все 11 со сдвигом −7 и т. д.); средние тоже идут блоками (11 `past7`, затем 11 `next7`), а в списке они чередуются парами. Совпадают только первые 20 имён и последнее (`f_diff_max_pm3`, столбец 130). Длина списка верна, на обучение это не влияет (модели работают с номерами столбцов), но использовать `tabular_names` для подписей важности признаков нельзя без исправления.

### Пример
```python
names = FeatureBuilder().tabular_names
names[0], names[19]    # ('working', 'oil_missing')
names[20], names[107]  # ('working@-14', 'oil_below_base@+14')  - по списку
names[130]             # 'f_diff_max_pm3'
```

Фактически в матрице столбец 20 — `working@-14`, но столбец 21 — `f_diff@-14` (а не `working@-7`), как и подсказывает порядок блоков. Проверка на синтетической скважине: `liq_vs_30d` в день 42 равен 0,105, и в день 35 это значение «через 7 дней» стоит не в столбце с именем `liq_vs_30d@+7` (индекс 50 в списке, там совсем другое имя), а в столбце 89 (`20 + 6·11 + 3`: сдвиг +7 — седьмой по порядку, `liq_vs_30d` — четвёртый канал).

## FeatureBuilder.sequence  [e66ea86a]
Возвращает матрицу `float32` формы `(число_дней, 20)`: столбцы — `SEQUENCE_CHANNELS` в заданном порядке, строки — дни `well.frame.index`. Длину ряда не меняет: Transformer должен выдать вероятность для каждого дня скважины.

Всю работу делает `_channels`, здесь только выбор и порядок столбцов. Значения лежат в [-3; 3], NaN нет.

### Пример
Синтетическая скважина, день 40 — день подъёма 48 → 50 Гц:

```python
s = fb.sequence(make_well())
s[40, fb.SEQUENCE_CHANNELS.index("f_diff")]        # 0.4: скачок на 4% частоты ×10
s[40, fb.SEQUENCE_CHANNELS.index("step_size")]     # 0.42
s[45, fb.SEQUENCE_CHANNELS.index("liq_vs_step")]   # около 0.10: дебит на 10% выше уровня до скачка
```

Это то, что проверяет `test_features_shapes_and_values`. На реальной скважине 8822 за день до начала по разметке (29.07.2022) `liq_vs_30d` = 0, а в день начала (30.07.2022) жидкость выросла со 157 до 197 м³/сут и `liq_vs_30d` = `liq_vs_step` = 0,25.

## FeatureBuilder.tabular  [61739ba0]
Возвращает матрицу `float32` формы `(число_дней, 131)` для scikit-learn. Собирает таблицу из блоков:

1. 20 основных каналов (как в `sequence`);
2. для 11 каналов `SHIFTED_CHANNELS` — значения через `offset` дней для каждого из 8 сдвигов. Положительный сдвиг означает «значение в будущем»: детекция офлайн, весь ряд известен, и именно будущее (дебит через неделю после скачка) говорит, был ли эффект. Пустые края (первые/последние дни) заполняются нулями;
3. средние за 7 дней назад (`_mean_past7`, включая сегодня) и за 7 дней вперёд (`_mean_next7`) — сглаживают шум суточных замеров;
4. `f_diff_max_pm3` — максимум `f_diff` в центрированном окне 7 дней (±3): «рядом был скачок частоты», чтобы дату начала можно было искать рядом со скачком.

Для Transformer всё это не нужно: свёртка и внимание сами смотрят на соседей. Для деревьев и логистической регрессии каждая строка независима, поэтому контекст кладётся в строку.

### Пример
Фактическая раскладка столбцов (индексы в матрице):

| Столбцы | Что |
|---------|-----|
| 0–19 | основные каналы |
| 20–107 | 8 блоков по 11 каналов: сдвиги −14, −7, −3, −1, +1, +3, +7, +14 |
| 108–118 | `_mean_past7` для 11 каналов |
| 119–129 | `_mean_next7` для 11 каналов |
| 130 | `f_diff_max_pm3` |

```python
t = fb.tabular(make_well())      # (120, 131)
t[35, 89]    # 0.105: liq_vs_30d через 7 дней (день 42, дебит 110 вместо 100)
t[40, fb.SEQUENCE_CHANNELS.index("f_diff")]   # 0.4 в день скачка
t[:, 130]    # 0.4 в днях 37…43 (скачок в день 40, окно ±3), иначе 0
```

Для 698 реальных скважин (201 918 дней) получается `(1587, 131)` на скважине 8822. Обучающих строк после `training_mask(45)` по всем скважинам — 14 247, из них 5 213 положительных.

## FeatureBuilder._channels  [f6ec4694]
Главный метод: считает DataFrame со всеми 20 каналами по таблице `well.frame` (колонки `state`, `frequency`, `debit_liquid`, `debit_oil`, `watercut`, `pressure_zab`). Шаги:

1. `working` = `state` > 0 и частота > 10 Гц.
2. Частота «лечится»: на остановках значение заменяется ближайшим рабочим (`where(working).ffill().bfill()`), иначе провал до 0 Гц превращался бы в огромный ложный «скачок» при запуске насоса.
3. Опорная частота (`reference`) — медиана по рабочим дням; `f_rel = f / reference − 1`. Если рабочих дней нет, опора = 1 (всё нулевое, но без деления на ноль).
4. `f_diff`, `f_above_min30`, `f_below_max30` — из `f_rel`, масштаб ×10, чтобы типичный подъём на 1 Гц давал ~0,2, а не 0,02.
5. Относительные изменения дебитов, давления и обводнённости — `_relative_to_past`, `_difference_to_past`.
6. Признаки от последнего скачка — `_since_last_step` (включая возврат нефти к базе).
7. `oil_missing` = 1 там, где нет замера нефти: иначе пропуск, заполненный нулём, выглядел бы как «нефть равна базе».
8. Итог: `fillna(0)` и `clip(−3; 3)`. Ограничение нужно, потому что в данных бывают выбросы (дебит вырос в 20 раз из-за ошибки замера), которые разрушили бы обучение.

Нули вместо NaN неоднозначны (0 — и «ничего не изменилось», и «нет данных»), поэтому отдельно есть `working`, `liq_missing` и `oil_missing`.

### Пример
Синтетическая скважина: частота 48 Гц, рабочая медиана `reference` = 50, значит до скачка `f_rel` = 48/50 − 1 = −0,04 (первый день `s[0, 1]` = −0,04), после — 0.

## FeatureBuilder._relative_to_past  [7ecb2bf0]
Относительное изменение показателя к его «недавнему уровню»: `value / median(прошлые 30 дней) − 1`, только для рабочих дней. Параметры: `series` — суточный ряд (дебит жидкости, нефти или забойное давление), `working` — маска работы насоса. Результат — Series с NaN на неработающих днях и там, где мало истории.

Детали, которые важны:

- `shift(1)` — окно **прошлого**, сегодняшний день в базу не входит, иначе эффект «размазывал» бы собственную базу;
- остановленные дни исключены из базы (`series.where(working)`), иначе нули остановки занижали бы медиану;
- нужно минимум 3 значения (`min_periods=3`), медиана — потому что устойчива к выбросам;
- ноль в базе заменяется NaN, чтобы не делить на ноль.

### Пример
Скважина 8822: 29.07.2022 дебит жидкости 157 м³/сут, медиана за прошлые 30 дней тоже 157 → 0. В день начала 30.07.2022 — 197 м³/сут → 197/157 − 1 ≈ 0,25 (это `liq_vs_30d` = 0,25 на реальных данных).

## FeatureBuilder._difference_to_past  [61b8a8ba]
То же, что `_relative_to_past`, но разностью и по **среднему**, а не медиане: `value − mean(прошлые 30 дней)`. Используется для обводнённости (`watercut`, %): она уже сама доля, относительное изменение от 5 % до 6 % выглядело бы как +20 %, а разность в процентных пунктах честнее. Деление на 10 в `_channels` приводит единицы к масштабу остальных каналов (рост обводнённости на 10 п.п. → 1,0).

### Пример
Обводнённость 90 % весь месяц и 92 % сегодня: разность 2 п.п. → после деления на 10 канал `wc_vs_30d` = 0,2. В синтетической скважине обводнённость константа 90 → канал везде 0.

## FeatureBuilder._since_last_step  [a6475c2a]
Признаки «относительно последнего подъёма частоты». Это то, как рассуждает детектор на правилах: ищем скачок и смотрим, что стало с дебитом после него.

Алгоритм:

1. Частота сглаживается скользящей медианой по 3 дням (убирает одиночные выбросы).
2. Скачок — день, где сглаженная частота выросла минимум на `MIN_STEP` = 0,1 Гц и насос работает.
3. Ряд делится на отрезки «от скачка до следующего скачка». Для каждого отрезка базой служит значение **за день до** скачка (`before`).
4. В отрезке: `days_since_step` = min(дни от скачка, 120) / 120; `step_size` = (f после − f до) / f до × 10; `liq_vs_step`, `oil_vs_step` — относительное изменение дебита к базе (через `_ratio`); `wc_vs_step` — разность обводнённости, /10.
5. До первого скачка `days_since_step` = 1 («давно не было»), остальные нули.

Дополнительно (окончание эффекта по нефти): `_base_level` считает базу по нефти, `_return_features` возвращает четыре признака без префикса, а здесь они записываются как `oil_vs_base`, `oil_below_base`, `oil_days_below`, `oil_drawdown`. Если базы нет, эти колонки в отрезке остаются нулями. Методы обобщены (работают с любым дебитом): по жидкости те же признаки проверены на `compare` и убраны, устойчивого выигрыша они не дали.

Возвращает DataFrame с девятью колонками на индексе `frame`.

### Пример
Синтетическая скважина (скачок 48 → 50 Гц в день 40): `step_size` = 0,42 с дня 40, `days_since_step` = 0 в день 40, 1/120 ≈ 0,01 в день 41, 2/120 ≈ 0,02 в день 42; а `liq_vs_step` = 0,10 с дня 42, когда дебит стал 110 вместо 100. Нефть там равна 0,1 · жидкость: база 10, `oil_vs_base` = 0,1 в днях 42–71, `oil_below_base` = 1 с дня 72, `oil_days_below` в день 72 = 1/14 ≈ 0,07. Скважина 8822 в день разметки: `days_since_step` = 0,02 (около 3 дней после последнего скачка).

## FeatureBuilder._base_level  [687bb232]
Уровень дебита до подъёма: медиана за `BASE_DAYS` = 3 дня перед скачком и сам день скачка (пропуски отброшены). Параметры: `debit` — суточный ряд дебита (в проекте вызывается для нефти `debit_oil`), м³/сут; `step` — индекс дня скачка. Возвращает число или `None`, если замеров нет или база <= 0 (делить на неё нельзя).

**Почему медиана за несколько дней.** Буквальное «сырой дебит в день начала» совпало с датой окончания технолога (±3 дня) только в 27 % случаев из-за шума одного дня; медиана за 3 дня плюс день скачка и правило «нефть не выше базы» — в 61 % (±3) и 70 % (±7) на 343 мероприятиях (анализ разметки).

### Пример
Синтетическая скважина (`make_well()`, нефть = 0,1 · жидкость = 10 м³/сут, скачок в день 40):

```python
fb._base_level(well.frame["debit_oil"].to_numpy(), 40)   # 10.0
fb._base_level(np.full(120, np.nan), 40)                 # None
```

## FeatureBuilder._return_features  [d013326f]
Четыре признака «дебит относительно базы» для отрезка после скачка. Параметры: `debit` — дебит отрезка (нефть), `base` — результат `_base_level`. Возвращает словарь массивов с именами без префикса (`_since_last_step` добавляет `oil_`):

- `vs_base` = дебит / база − 1;
- `below_base` = 1, если дебит <= базы;
- `days_below` = число дней подряд ниже базы, /14, не больше 1;
- `drawdown` = (максимум дебита с начала отрезка − дебит) / база.

День без замера не несёт сведений: отношение 0, он не считается «ниже базы» и обрывает серию. Иначе дыра в замерах выглядела бы как возврат к базе.

### Пример
Синтетическая скважина (после префикса `oil_` это колонки таблицы): база 10, в днях 42–71 нефть 11, затем снова 10.

| День | `oil_vs_base` | `oil_below_base` | `oil_days_below` | `oil_drawdown` |
|------|---------------|------------------|------------------|----------------|
| 45 | 0,10 | 0 | 0 | 0 |
| 72 | 0 | 1 | 0,07 (1/14) | 0,10 |
| 90 | 0 | 1 | 1 (серия насытилась) | 0,10 |

## _ratio  [17d118a3]
Относительное изменение массива к базовому значению: `values / base − 1`. Если база не задана, NaN или 0, возвращает нули — когда уровень «до скачка» неизвестен, признак не должен выдумывать эффект.

### Пример
