## @module  [4996fec6]
Тесты `data/repair.py`: проверка разметки по частоте (`FrequencyCheck`) и исправление сдвинутых блоков (`BlockShiftRepair`). Это самое хрупкое место данных: объединённая статистика 2021–2026 склеена макросом, и часть выгрузок записана на 180 дней позже. В тестах сдвиг короче — `SHIFT = 30` дней, чтобы всё помещалось в ряд из 120 дней; логика та же, поэтому `BlockShiftRepair` создаётся как `BlockShiftRepair(shifts=(0, SHIFT))`.

Общая синтетическая картина (`_shifted_block`): шесть скважин, блок данных на 60 дней записан на 30 дней позже, чем надо. Запуск файла:

```bash
.venv/Scripts/python -m pytest gtm_detector/ml_freq/tests/test_repair.py -q
```

## test_frequency_check  [bcc882e6]
**Что проверяет.** Решение `FrequencyCheck.confirms`: поднялась ли частота у даты начала так, как записано в разметке.

**Данные.** Ряд из 40 дней: 20 дней по 48 Гц, потом 20 дней по 50 Гц; технолог указал «48 → 50», скачок на 20-м дне.

| Вызов | Ответ | Почему |
|-------|-------|--------|
| `confirms(series, 20, 48, 50)` | `True` | подъём ровно в указанный день |
| `confirms(series, 18, 48, 50)` | `True` | дата технолога на 2 дня раньше скачка, допуск ±3 дня |
| `confirms(series + 3, 20, 48, 50)` | `True` | телеметрия смещена на 3 Гц, но прирост (2 Гц, т.е. не меньше половины запланированных) тот же |
| `confirms(series, 20, 48, 56)` | `False` | запланировано +8 Гц, фактически +2 — меньше половины |
| `confirms(const 48, 20, 48, 50)` | `False` | подъёма нет |
| `confirms(NaN, 20, 48, 50)` | `None` | замеров нет — проверить нельзя, это не опровержение |

**Какую ошибку поймал бы.** Ужесточение или ослабление проверки: от неё зависит, какие мероприятия разметки допускаются к обучению и какой сдвиг блока считается подтверждённым. Отдельно важно различие `False` и `None`: «нет данных» не должно голосовать против сдвига.

```bash
.venv/Scripts/python -m pytest gtm_detector/ml_freq/tests/test_repair.py::test_frequency_check -q
```

## _shifted_block  [aed2228b]
Вспомогательная функция (не тест): строит данные для остальных тестов файла. Возвращает матрицу частот `frequency` (6 скважин × 120 дней, пропуски — `NaN`), маску присутствия данных `presence`, список `LabelPoint` и календарь, начинающийся 01.01.2026.

Устройство: у скважины `k` (0–5) разметка говорит «48 → 50 Гц в день `10 + k`». Но в файле блок записан на 30 дней позже: дни 30–89 заполнены (48 Гц, с дня `40 + k` — 50 Гц), остальное `NaN`. Правильный сдвиг, значит, 30; при «сдвиге 0» подъёма в нужных днях нет вообще.

### Пример
```python
frequency, presence, labels, dates = _shifted_block()
frequency.shape      # (6, 120)
labels[:2]           # [LabelPoint(row=0, day=10, current=48.0, new=50.0),
                     #  LabelPoint(row=1, day=11, current=48.0, new=50.0)]
dates[30]            # Timestamp('2026-01-31') - первый день блока
```

## test_repair_finds_and_undoes_shift  [52928724]
**Что проверяет.** Весь путь исправления: найти сегмент → оценить сдвиг → применить.

**Проверки:**

1. `segments(presence, dates)` находит один сегмент — дни 30–89 (`SHIFT … SHIFT+59`): там 6 скважин появились и исчезли разом, а пустые края сегментами не считаются;
2. после `assess` у сегмента `shift == 30`; доказательства по разметке: для сдвига 30 подтверждено 6 мероприятий, для сдвига 0 — ни одного (в днях 10–15 данных нет, проверить нечем);
3. после `apply` блок вернулся на место: в днях 60 и позже только `NaN`, а у скважины 0 частота 48 Гц в день 9 и 50 Гц в день 10 — как в разметке.

**Какую ошибку поймал бы.** Сдвиг в обратную сторону, ошибку на единицу при переносе столбцов, потерю данных блока. Если сломается этот тест, обучение пойдёт на рядах, где подъём частоты и разметка не совпадают на полгода.

## test_seam_takes_neighbour_decision  [94ff9224]
**Что проверяет.** Обработку **стыка** выгрузок: сегмента в 1 день, который проверить нечем, потому что мероприятий там нет.

**Данные.** К шести скважинам добавлены ещё пять, у которых данные есть только в день 29, прямо перед блоком. Появляется сегмент из одного дня (29) и основной сегмент 30–89.

**Ожидание.** `segments[0].days == 1`, и у стыка то же решение, что у соседа: `shift == 30`. Без этого один день на границе остался бы на месте со сдвигом 0 и «торчал» бы из блока.

**Какую ошибку поймал бы.** Дырки и дубли на границах склейки выгрузок; решение для коротких сегментов, принимаемое по пустому множеству доказательств.

## test_censored_label  [2946ce15]
**Что проверяет.** Обработку мероприятий со статусом «ПРОДОЛЖАЕТСЯ ЭФФЕКТ» (`censored=True`): наблюдение остановлено, но эффект продолжался. Тест проверяет `WellSeries.training_mask` и `EventMatcher`.

**Данные.** `make_well(n_days=200, step=40, effect=30)`; разметку заменили на тот же интервал с `censored=True` (начало 12.02.2026, «конец» 13.03.2026 — только последний день наблюдения).

**Проверки:**

- в `training_mask(45)` нет ни одного дня после 13.03.2026 (маска 72 дня — с самого начала ряда по день 71), хотя без `censored` в неё вошли бы ещё 45 дней: после последнего наблюдения про эффект ничего не известно, и штрафовать модель за «эффект» там нельзя;
- модель нашла мероприятие 12.02.2026 — 31.05.2026 (день 150): `true_positives == 1`, `end_errors == []`, `open_ends == 0`. Окончание у цензурированной метки не сравнивается: конец эффекта неизвестен.

**Какую ошибку поймал бы.** Штраф за правильно найденный длинный эффект (метрики окончания занизились бы), обучение на «пустых» днях после обрыва мониторинга.
