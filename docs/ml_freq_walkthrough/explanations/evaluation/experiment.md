## @module  [3811bce1]
Перекрёстная проверка: честный ответ на вопрос «какая модель лучше». Модуль берёт набор размеченных скважин, делит его на фолды **по скважинам**, для каждой модели по очереди учит на четырёх фолдах и проверяет на пятом, а потом собирает результаты в `ModelResult`.

Почему по скважинам, а не по дням: соседние дни одной скважины почти одинаковы. Если дни одной скважины попадут и в обучение, и в проверку, модель «узнает» скважину, и метрики будут завышены (утечка между скважинами — первое правило ML-части проекта).

Все модели получают **одинаковые фолды** (их считает `folds` один раз из `ExperimentConfig.seed`), один `SegmentDecoder` и один `EventMatcher`. Результат передаётся в `ComparisonReport`.

## ModelResult  [40bb6b2c]
Итог проверки одной модели (изменяемый `dataclass`).

| Поле | Смысл |
|------|-------|
| `name` | ключ в `model_registry()`: `transformer`, `gboost`… Используется как имя листа в Excel |
| `title` | читаемое название: «Градиентный бустинг (HistGB)» |
| `score` | суммарный `Score` по всем тестовым скважинам всех фолдов |
| `day_auc` | ROC-AUC по дням: качество вероятностей **до** декодирования |
| `train_seconds` | время `fit` по всем фолдам, секунды |
| `predictions` | строки «метка — найдено» для листа с предсказаниями |

### Пример
Для `gboost` в `results/ml_freq/comparison_merged/сравнение_качества_моделей_(21-26 год).xlsx`: `score` — TP 84, FN 51, FP 143; `day_auc` = 0,917; `train_seconds` = 112,2; `predictions` — 135 строк (по одной на размеченное мероприятие).

## ModelResult.as_row  [9a4828c4]
Превращает результат в одну строку таблицы сравнения: «модель» (это `title`), все метрики из `Score.as_dict()`, «ROC-AUC по дням» и «обучение, с (все фолды)» (секунды, округлено до 0,1). Из таких строк `ComparisonReport.table` собирает лист «Сравнение».

```python
result.as_row()['ROC-AUC по дням']   # 0.917137 для gboost
result.as_row()['обучение, с (все фолды)']   # 112.2
```

## CrossValidator  [d4b0ec71]
Считает метрики моделей методом k-fold по скважинам. Отдельные шаги: `folds` — разбиение, `run` — цикл по моделям, `_evaluate` — проверка одной модели, `_rows` — строки для листа предсказаний.

ROC-AUC считается **по всем дням всех тестовых скважин сразу** (вероятности и целевые значения склеиваются в два длинных массива), а не по скважинам с последующим усреднением: в отдельной скважине может не быть ни одного дня эффекта, и для неё AUC не определён.

Команда: `python -m gtm_detector.ml_freq compare --models gboost extra_trees` (около 2 минут), все модели — около 15 минут.

## CrossValidator.__init__  [3146393b]
Принимает `ExperimentConfig` или `None` (по умолчанию `folds=5`, `seed=0`, `start_tolerance=7`, `DecoderConfig()`). Создаёт `SegmentDecoder` и `EventMatcher` из этого же конфига — чтобы декодирование и допуск были одинаковы у всех моделей.

В `cli.run_compare`: `CrossValidator(ExperimentConfig(folds=args.folds, seed=args.seed))`. Ключи `--folds` и `--seed` попадают сюда.

```python
cv = CrossValidator()
cv.matcher.start_tolerance   # 7
cv.decoder.config.threshold  # 0.5
```

## CrossValidator.folds  [12a4907a]
Возвращает список из `config.folds` списков индексов скважин. Индексы перемешиваются генератором `np.random.default_rng(seed)` (воспроизводимо, без глобального `np.random`), затем делятся `np.array_split` на почти равные части.

Получается не «кусок подряд из Excel», а случайная выборка скважин: иначе соседние скважины одного куста (похожие по условиям) попадали бы в один фолд. Фолды одни и те же для всех моделей при том же `seed`.

```python
CrossValidator().folds([None] * 12)
# [[9, 2, 7], [4, 5, 11], [0, 3], [6, 10], [8, 1]]
```

На 122 размеченных скважинах объединённого набора фолды получаются размером 25, 25, 24, 24, 24.

## CrossValidator.run  [da274b29]
Принимает скважины `wells` (только с разметкой) и словарь `{имя: фабрика_модели}` — обычно часть `model_registry()`. Фолды считаются один раз, затем для каждой модели вызывается `_evaluate`. Возвращает `list[ModelResult]` в порядке словаря.

Модель передаётся **фабрикой** (вызываемым без аргументов), а не готовым объектом: на каждом фолде нужна свежая, необученная копия, иначе знания о предыдущем фолде утекли бы в следующий.

```python
results = CrossValidator().run(wells, {"gboost": registry["gboost"]})
results[0].title   # 'Градиентный бустинг (HistGB)'
```

## CrossValidator._evaluate  [4d6312a1]
Проверка одной модели. Для каждого из k фолдов:

1. `train` — все скважины, **кроме** тестовых; `factory()` создаёт новую модель; `model.fit(train)` замеряется по времени (секунды суммируются в `train_seconds`).
2. Для каждой тестовой скважины: `predict_proba(well)` → вероятности по дням; `well.target()` — истинные дни эффекта; `decoder.decode` → интервалы; `matcher.score` → `Score`, который прибавляется к `result.score`; `_rows` добавляет строки в `result.predictions`.

После всех фолдов дневные массивы склеиваются и считается `roc_auc_score`. Если в данных нет ни одного дня эффекта или все дни — эффект, AUC не определён, записывается `nan`. Фиксируется только `title` первой модели фолда: `ModelResult` создаётся лениво, потому что название известно лишь у объекта модели.

Обучение идёт по `training_mask` (±45 дней вокруг размеченных мероприятий — `CONTEXT_DAYS`), это делает сама модель в `fit`, а проверка идёт по **всему** ряду тестовой скважины: именно так модель будет работать в `predict`.

В лог (`-v`) пишется «gboost: фолд 3/5 готов» и итог «recall=0.622 F1=0.464».

## CrossValidator._rows  [3b11f757]
Строит строки листа предсказаний для одной скважины: по одной на каждую размеченную метку (из `matcher.match`). Столбцы: «скважина», «куст», «начало (разметка)», «окончание (разметка)», «начало (модель)», «окончание (модель)», «Δ начала, дн», «Δ окончания, дн», «эффект продолжался».

Для ненайденной метки модельные поля пусты. «Δ окончания» заполняется только когда у обеих сторон есть конец и метка не `censored` — те же правила, что в `EventMatcher.score`.

Строки листа `gboost` из `comparison.xlsx`:

| скважина | куст | начало (разметка) | начало (модель) | Δ начала, дн | Δ окончания, дн | эффект продолжался |
|----------|------|-------------------|-----------------|--------------|-----------------|--------------------|
| 8822 | 615А | 30.07.2022 | 29.07.2022 | −1 | −1 | False |
| 25571 | 2161 | 30.08.2022 | 31.08.2022 | 1 | — | True |
| 32416 | 1910 | 25.11.2024 | — (не найдено) | — | — | True |

Лист нужен, чтобы увидеть, на каких скважинах модель промахнулась, и показать это технологам.
