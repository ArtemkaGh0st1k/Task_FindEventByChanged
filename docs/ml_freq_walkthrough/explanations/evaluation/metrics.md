## @module  [179212ec]
Как понять, что модель «нашла мероприятие». Модуль сопоставляет интервалы модели (`predicted`) с разметкой технологов (`labels`) и считает метрики уровня **мероприятий**, а не дней.

Ключевые решения:

- **Сопоставление один к одному по дате начала с допуском ±7 дней** (`EventMatcher`). Одно найденное мероприятие не может «подтвердить» две строки разметки, а одна строка разметки — два найденных.
- **Ошибка окончания не считается для `censored`**: у мероприятий «ПРОДОЛЖАЕТСЯ ЭФФЕКТ» дата окончания в разметке — просто конец наблюдений, а не конец эффекта.
- **Precision занижена намеренно**: разметка неполная, и модель может найти настоящий подъём частоты, которого технолог не записал; он считается «ложным». Поэтому главные метрики — recall и точность дат.

Метрики по скважинам складываются оператором `+` (`Score.__add__`), так что итог по модели — сумма по всем тестовым скважинам всех фолдов.

## _share  [66454674]
Доля ошибок, не превышающих `days` по модулю. Принимает список целых ошибок в днях (`найдено − разметка`), возвращает число 0…1, а для пустого списка — `nan` (а не 0: «нечего измерять» не то же самое, что «всё плохо»).

```python
_share([-1, 1, 5, 0], 1)   # 0.75: три из четырёх ошибок в пределах ±1 день
_share([], 3)              # nan
```

Из неё получаются столбцы «начало: точно» (`days=0`), «начало: ±1 дн», «начало: ±3 дн», «конец: ±3 дн», «конец: ±7 дн».

## _mae  [c1d5420c]
Средняя абсолютная ошибка в днях; для пустого списка — `nan`.

```python
_mae([-1, 1, 5, 0])   # 1.75
```

В `comparison.xlsx` для `gboost`: «начало: MAE, дн» = 1,86, «конец: MAE, дн» = 20,5. Окончание ошибается сильнее: конец эффекта размыт, а редкие большие промахи (десятки дней) тянут среднее вверх.

## Score  [1f8e4506]
Счётчики и списки ошибок, из которых получаются все метрики. Поля:

| Поле | Смысл |
|------|-------|
| `true_positives` (TP) | размеченное мероприятие нашлось |
| `false_negatives` (FN) | размеченное не нашлось |
| `false_positives` (FP) | найденное не соответствует разметке |
| `start_errors` | `начало модели − начало разметки`, дни, по каждой паре TP |
| `end_errors` | то же для окончания, только для пар с известным концом |
| `open_ends` | в разметке конец есть, а модель считает эффект продолжающимся — ошибка окончания не определена |

Класс — обычный изменяемый `dataclass`, у него нет допущений о скважинах: его можно складывать.

### Пример
Реальные цифры `gboost` из `results/ml_freq/comparison_merged/…(21-26 год).xlsx`: TP = 84, FN = 51, FP = 143, «не закрыт конец» = 1. Всего размеченных мероприятий 84 + 51 = 135 — столько же, сколько строк на листе `gboost`.

## Score.recall  [369c0c67]
`TP / (TP + FN)` — доля размеченных мероприятий, которые модель нашла. Если размеченных нет — 0.

```python
Score(true_positives=84, false_negatives=51).recall   # 0.6222
```

Это столбец «найдено размеченных (recall)». Для сравнения: детектор на правилах из ветки `feature/increase-f-gtm` находит 89 %.

## Score.precision  [bb28eaaf]
`TP / (TP + FP)` — какая часть найденного совпала с разметкой. Нет найденного — 0.

```python
Score(true_positives=84, false_positives=143).precision   # 0.3700
```

Низкое значение не означает, что 63 % найденного — ошибки: часть FP — настоящие подъёмы частоты, не внесённые в разметку.

## Score.f1  [241d62c2]
Гармоническое среднее precision и recall; 0, если оба нуля. По F1 сортируется таблица сравнения.

```python
Score(true_positives=84, false_positives=143, false_negatives=51).f1   # 0.4641 (в отчёте 0.464088)
```

## Score.__add__  [fdb55550]
Складывает два `Score`: счётчики суммируются, списки ошибок объединяются. Возвращает новый объект. Нужно, чтобы накопить результат по всем скважинам: `result.score += matcher.score(predicted, well.labels)` в `CrossValidator._evaluate`.

Важно: складываются **ошибки**, а не доли, поэтому итоговая точность даты — это доля по всем мероприятиям, а не среднее долей по скважинам.

```python
a = Score(1, 2, 3, [1], [2], 0)
a + a
# Score(true_positives=2, false_positives=4, false_negatives=6, start_errors=[1, 1], end_errors=[2, 2], open_ends=0)
```

## Score.as_dict  [8af17647]
Все метрики одним словарём с русскими названиями — это заголовки столбцов листа «Сравнение» в `comparison.xlsx`: recall, precision, F1, доли начала «точно / ±1 / ±3», MAE начала, доли конца «точно / ±3 / ±7», MAE конца, TP, FN, FP, «не закрыт конец». Метрики даты считаются только по найденным парам.

```python
# Score после примера в EventMatcher.score
{'найдено размеченных (recall)': 1.0, 'точность (precision)': 0.667, 'F1': 0.8,
 'начало: точно': 0.0, 'начало: ±1 дн': 0.5, 'начало: ±3 дн': 1.0, 'начало: MAE, дн': 1.5,
 'конец: точно': 0.0, 'конец: ±3 дн': 1.0, 'конец: ±7 дн': 1.0, 'конец: MAE, дн': 2.0,
 'TP': 2, 'FN': 0, 'FP': 1, 'не закрыт конец': 0}
```

## EventMatcher  [3d5c02db]
Сопоставляет найденные интервалы с размеченными. Пара допустима, только если даты начала различаются не более чем на `start_tolerance` дней (по умолчанию 7, `ExperimentConfig.start_tolerance`). Из всех допустимых пар сначала берутся самые близкие; каждый найденный и каждый размеченный интервал используется не более одного раза.

Почему «один к одному»: иначе одно длинное найденное мероприятие засчитывалось бы сразу за несколько размеченных, а recall оказался бы завышен. Окончание в сопоставлении не участвует: сначала находим мероприятие по началу, затем отдельно смотрим, насколько точно угадан конец.

## EventMatcher.__init__  [7db83775]
Принимает `start_tolerance` — допуск в днях. Значение 7 одинаково для всех моделей (его передаёт `CrossValidator` из конфига), поэтому сравнение честное.

```python
EventMatcher().start_tolerance   # 7
```

## EventMatcher.match  [b1e46d9d]
Принимает найденные интервалы `predicted` и размеченные `labels`. Возвращает список пар `(метка, найденный | None)` **по одной на каждую метку**, в порядке меток; `None` — не нашли.

Алгоритм жадный: все допустимые пары сортируются по `(|Δ начала|, номер найденного, номер метки)`, затем проходом по списку берутся пары, где ни найденное, ни метка ещё не заняты. При равном расстоянии выигрывает найденный интервал с меньшим номером, то есть более ранний.

Ненайденные интервалы (лишние) в результат не попадают — их считает `score` как FP. По этой функции `CrossValidator._rows` строит листы с предсказаниями по каждой модели.

### Пример
Скважина с двумя метками: подъём 14.08.2023 (до 20.09) и мероприятие 01.12.2023 с пометкой «продолжается» (`censored=True`). Модель нашла три интервала:

```python
labels = [Interval(date(2023, 8, 14), date(2023, 9, 20)),
          Interval(date(2023, 12, 1), date(2023, 12, 31), censored=True)]
predicted = [Interval(date(2023, 8, 15), date(2023, 9, 22)),
             Interval(date(2023, 12, 3), None),
             Interval(date(2024, 3, 1), date(2024, 3, 9))]
EventMatcher().match(predicted, labels)
# [(метка 14.08, найдено 15.08–22.09), (метка 01.12, найдено 03.12–…)]
```

Третий интервал (01.03.2024) пары не нашёл — он лишний и будет учтён как FP.

## EventMatcher.score  [73beb439]
Строит `Score` для одной скважины: сопоставляет через `match` и считает:

- нет пары с меткой → `false_negatives += 1`;
- есть пара → `true_positives += 1`, в `start_errors` добавляется `найденное_начало − начало_метки` в днях (отрицательное — модель раньше технолога);
- ошибка окончания записывается, только если у метки есть конец **и** она не `censored`; если при этом модель считает эффект продолжающимся (`end=None`), увеличивается `open_ends`, а не `end_errors`;
- `false_positives = len(predicted) − TP`.

Для примера из `match`: TP = 2, FN = 0, FP = 1; ошибки начала `[1, 2]` (MAE 1,5), ошибка окончания одна: `22.09 − 20.09 = 2` дня. Вторая метка `censored`, поэтому её конец в метрику не идёт. Это правило объясняет, почему у `gboost` «конец» оценён по ~60 мероприятиям из 84 найденных.

```python
EventMatcher().score(predicted, labels).as_dict()['конец: ±3 дн']   # 1.0
```
