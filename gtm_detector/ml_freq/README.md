# ml_freq — ML-детекция ГТМ «увеличение частоты F»

Собственная нейросеть (**Transformer-энкодер для временных рядов, PyTorch**) и
готовые модели **scikit-learn** на одной задаче: по суточным замерам скважины
найти мероприятия «увеличение частоты F» и даты их начала и окончания.

Модуль самостоятельный: своё чтение Excel, свои метрики, от других пакетов
проекта не зависит.

## Быстрый старт

Из корня проекта (`.venv` проекта, зависимости из `req.txt`):

```bash
python -m gtm_detector.ml_freq compare                       # сравнить все модели (~15 мин на CPU)
python -m gtm_detector.ml_freq compare --models gboost extra_trees   # только выбранные
python -m gtm_detector.ml_freq train --model transformer     # обучить на всей разметке, сохранить веса
python -m gtm_detector.ml_freq predict --model transformer   # найти мероприятия без разметки
python -m gtm_detector.ml_freq audit                         # отчёт о качестве данных 2021–2026
python -m pytest gtm_detector/ml_freq/tests                  # тесты
```

Данные по умолчанию — объединённые файлы 2021–2026 (`--dataset merged`):
`resources/Статистика_с_2021_2026_в_одном_файле.xlsx` (замеры) и
`resources/Итоговый_файл_c_2021_2026.xlsx` (разметка; «c» в имени латинская).
Первые тестовые файлы из `resources/test_datas` — `--dataset test`.
Первое чтение Excel ~30 с, дальше — из кэша (`%TEMP%/gtm_ml_freq_cache`) за доли секунды.

## Данные 2021–2026 и их исправление

Статистика склеена макросом из отдельных выгрузок, и часть выгрузок записана
**на 180 дней позже**. Подробно — в docstring и выводе `audit.py`; кратко:

1. Календарь делится на **сегменты** — периоды с одним набором скважин (след одной выгрузки).
2. Для каждого сегмента проверяются сдвиги 0 и 180 дней: по исходной выгрузке
   (`resources/test_datas/input_dataset.xlsx`, есть для 2026 г.) и по разметке —
   на дату начала мероприятия частота должна подняться.
3. Подтверждённый сдвиг применяется; сегмент, где доказательства противоречат
   обоим вариантам, **исключается** (17 % ячеек), где проверить нечем — остаётся на месте.
4. Мероприятие разметки идёт в обучение, только если замеры после исправления
   подтверждают подъём частоты около даты начала.

Почему исключаются сегменты, а не скважины целиком: сдвиг — свойство выгрузки,
у одной скважины одни годы стоят верно, другие сдвинуты. Целиком не используются
только 70 скважин без телеметрии частоты.

Итог: из 786 строк итогового файла в обучение идут **135 мероприятий на 122 скважинах**;
остальные: скважины нет в статистике (333 — почти весь 2025 г.), нет замеров около
даты (153), замеры не подтверждают подъём частоты (89), дубликаты (30) и др.
Мероприятия «ПРОДОЛЖАЕТСЯ ЭФФЕКТ» (40) — конец наблюдения не равен концу эффекта:
после него дни не используются при обучении, ошибка окончания не считается.

`audit` пишет `results/ml_freq/data_audit/data_audit.xlsx` (сегменты, решение по
каждой строке разметки, статус каждой скважины) и `data_audit.png` (скважин с
замерами по дням до и после исправления).

Результаты:

| Команда   | Что пишет                                                                    |
|-----------|------------------------------------------------------------------------------|
| `compare` | `results/ml_freq/<дата_время>/comparison.xlsx` (метрики + предсказания по каждой модели), `comparison.png` |
| `train`   | `gtm_detector/ml_freq/weights/<модель>.pt` или `.joblib`                      |
| `predict` | `results/ml_freq/<дата_время>/events_<модель>.xlsx`                           |

Модели: `transformer`, `logreg`, `random_forest`, `extra_trees`, `gboost`.

## Постановка задачи

Все модели решают одну задачу — **разметку ряда по дням**: для каждого дня
вероятность того, что идёт эффект мероприятия (день между датами начала и
окончания мониторинга в разметке).

Из вероятностей мероприятия получает общий `SegmentDecoder`, одинаково для всех моделей:

1. вероятности сглаживаются скользящим средним за 5 дней;
2. дни с вероятностью > 0.5 — «в эффекте»;
3. разрывы до 3 дней склеиваются, периоды короче 2 дней отбрасываются;
4. начало мероприятия — первый день периода, окончание — последний;
   период, дошедший до конца данных, — «эффект продолжается».

### Почему учимся не на всех днях

В разметке только мероприятия из списка рекомендаций. Реальных подъёмов частоты
в данных больше, и вне разметки «эффекта нет» не значит, что его действительно нет.
Если учить модели на всех днях, они получают противоречивые примеры. Поэтому
обучение идёт только на днях **±45 дней вокруг размеченных мероприятий**
(`WellSeries.training_mask`, `CONTEXT_DAYS` в `config.py`). Это подняло
полноту деревьев с 56 до 69 %.

## Признаки (`features/builder.py`)

15 каналов на каждый день:

| Канал                          | Смысл                                                            |
|--------------------------------|------------------------------------------------------------------|
| `working`                      | скважина работает: F > 10 Гц (в тестовых данных ещё и состояние «раб.»/«нак») |
| `f_rel`, `f_diff`              | частота относительно медианы скважины и её суточное изменение (50- и 150-Гц двигатели сопоставимы) |
| `f_above_min30`, `f_below_max30` | частота относительно минимума / максимума за 30 дней           |
| `liq_vs_30d`, `oil_vs_30d`, `wc_vs_30d`, `pzab_vs_30d` | Qж, Qн, обводнённость, Рзаб относительно прошлых 30 дней |
| `days_since_step`, `step_size` | дней с последнего подъёма частоты и его величина                 |
| `liq_vs_step`, `oil_vs_step`, `wc_vs_step` | Qж, Qн, обводнённость относительно дня перед подъёмом частоты |
| `liq_missing`                  | замера Qж нет                                                    |

Transformer получает эти каналы как последовательность. Моделям scikit-learn
каждый день виден отдельно, поэтому им добавлен контекст: сдвиги каналов на
±1, 3, 7, 14 дней и средние за 7 дней до и после — всего 106 признаков.

## Модели

### Собственная: Transformer для временных рядов (`models/transformer.py`)

```
признаки дня (15) ─► Conv1d, ядро 5 (локальные ступеньки частоты и дебита)
                 ─► + синусоидальное позиционное кодирование
                 ─► 2 × TransformerEncoderLayer (d_model 32, 4 головы внимания, pre-norm)
                 ─► LayerNorm + Linear ─► логит «день внутри эффекта»
```

- ~20 тыс. параметров; модель двунаправленная — детекция офлайн, весь ряд известен.
- Обучение: случайные окна по 128 дней вокруг размеченных мероприятий (аугментация),
  BCE с весом положительного класса, AdamW + косинусное расписание, 80 эпох.
- Крупнее (d_model 64, 3 слоя, ~105 тыс. параметров) — хуже: на ~100 скважинах
  модель переобучается.

### Готовые модели scikit-learn (`models/classic.py`)

| Имя             | Модель                                            |
|-----------------|---------------------------------------------------|
| `logreg`        | логистическая регрессия (+ стандартизация), линейная база |
| `random_forest` | случайный лес, 300 деревьев                        |
| `extra_trees`   | Extra Trees, 300 деревьев                          |
| `gboost`        | градиентный бустинг `HistGradientBoostingClassifier` |

У всех — веса классов «balanced» (дней эффекта меньше).

## Как оценивается (`evaluation/`)

- **Перекрёстная проверка по скважинам, 5 фолдов** (`CrossValidator`): модель не
  видит скважины, на которых её проверяют; разбиения одинаковы для всех моделей.
- **Сопоставление** (`EventMatcher`): найденное и размеченное мероприятие — одно и
  то же, если даты начала отличаются не больше чем на 7 дней; один-к-одному,
  сначала ближайшие пары.
- **Метрики** (`Score`): доля найденных размеченных мероприятий (recall), точность
  (precision), F1, точность дат начала и окончания (точно / ±1 / ±3 / ±7 дней),
  ROC-AUC по дням — качество вероятностей до декодирования.

Точность (precision) по этой разметке занижена: в ней не все реальные подъёмы
частоты, поэтому найденное «вне разметки» — не обязательно ошибка.

## Результаты

### Данные 2021–2026 (по умолчанию)

135 мероприятий на 122 скважинах (после исправления и проверки, см. выше).
Перекрёстная проверка по скважинам, 5 фолдов (`python -m gtm_detector.ml_freq compare`):

|------------------------------|-----------------|----------------------------|---------------------------|-----------------|------|---------------------|
| Случайный лес                | 61 %            | 14 / 46 / 78 %             | **12 / 56 / 68 %**        | **0.92**        | **0.48** | 42 с            |
| Extra Trees                  | 61 %            | 13 / 45 / 77 %             | 3 / 45 / 66 %             | **0.92**        | **0.48** | 35 с            |
| Градиентный бустинг (HistGB) | **62 %**        | **18 / 51 / 81 %**         | 5 / 36 / 54 %             | **0.92**        | 0.46 | 112 с               |
| **Transformer (своя модель)**| 48 %            | 17 / 46 / **83 %**         | 9 / 19 / 36 %             | 0.83            | 0.34 | 25 мин              |
| Логистическая регрессия      | 48 %            | 9 / 40 / 77 %              | 4 / 22 / 27 %             | 0.86            | 0.29 | 25 с                |

Ошибка окончания не считается для 40 мероприятий «ПРОДОЛЖАЕТСЯ ЭФФЕКТ».

По сравнению с тестовыми данными 2026 г. (ниже): ±3 дня по началу — на том же
уровне (77–83 %), а «точно в день» заметно ниже (13–18 % против 24–45 %). Ошибки
начала распределены симметрично около нуля (медиана 0–1 день), систематического
сдвига нет: даты в разметке 2021–2025 гг. просто менее точны относительно дня
изменения частоты. Полнота упала с ~69 до ~61 %: разметка разнороднее (пять лет,
разные цеха), а мероприятий почти столько же — 135 против 117, потому что большая
часть итогового файла не находит пары в статистике (см. `audit`).

### Тестовые данные 2026 г. (`--dataset test`)

Данные: 516 скважин, 01.01–31.08.2026; разметка — 117 мероприятий на 105 скважинах.
Перекрёстная проверка по скважинам, 5 фолдов (`python -m gtm_detector.ml_freq compare --dataset test`):

| Модель                       | Найдено размеч. | Начало: точно / ±1 / ±3 дн | Конец: точно / ±3 / ±7 дн | ROC-AUC по дням | F1   | Обучение (5 фолдов) |
|------------------------------|-----------------|----------------------------|---------------------------|-----------------|------|---------------------|
| Extra Trees                  | **69 %**        | 26 / 59 / 78 %             | 20 / 62 / **70 %**        | **0.89**        | **0.50** | 14 с            |
| Градиентный бустинг (HistGB) | 68 %            | **45 / 68 / 85 %**         | **33** / 57 / 67 %        | **0.89**        | 0.46 | 75 с                |
| Случайный лес                | 61 %            | 30 / 69 / 83 %             | 23 / 59 / 66 %            | 0.88            | 0.45 | 17 с                |
| Логистическая регрессия      | 61 %            | 28 / 52 / 73 %             | 3 / 27 / 38 %             | 0.81            | 0.34 | 9 с                 |
| **Transformer (своя модель)**| 50 %            | 24 / 52 / 78 %             | 21 / 43 / 50 %            | 0.83            | 0.31 | 12 мин              |

Для сравнения — детектор на правилах из ветки `feature/increase-f-gtm` на тех же
данных и той же схеме проверки: найдено **89 %**, начало точно / ±1 / ±3 —
**78 / 85 / 90 %**, конец точно / ±7 — **68 / 77 %** (там пара засчитывается ещё и
по «Дате выполнения» ±3 дня, поэтому сравнение слегка в его пользу).

Выводы:

- **Лучшие ML-модели — деревья** (Extra Trees, градиентный бустинг): находят
  ~70 % размеченных мероприятий, начало ±3 дня — в 78–85 % случаев. Бустинг точнее
  всех ставит даты, Extra Trees чуть больше находит.
- **Собственный Transformer слабее деревьев.** Причина — объём данных: ~85 скважин
  с ~95 мероприятиями в каждом обучающем фолде. Нейросеть с вниманием выигрывает
  на тысячах примеров; здесь деревья с явно заданным контекстом (сдвиги ±14 дней)
  эффективнее. Увеличение модели (d_model 64, 3 слоя) и обучения (80 эпох) не
  помогло: полнота осталась ~50 %.
- **Все ML-модели пока уступают правилам**, особенно по точной дате окончания.
  Правила напрямую кодируют то, как технологи закрывают эффект; модели должны
  выучить это из ~100 примеров.
- **Что даст рост:** больше подтверждённых мероприятий. Объединённые файлы
  2021–2026 дали лишь 135 вместо ~750 строк итогового файла: 333 строки — скважины,
  которых нет в статистике (почти весь 2025 г.), 153 — нет замеров около даты,
  17 % ячеек статистики исключены из-за неустранимого сдвига. Исходные выгрузки
  (до склейки) и статистика по скважинам 2025 г. — главный резерв.

## Архитектура

```
gtm_detector/ml_freq/
├── __main__.py, cli.py     python -m gtm_detector.ml_freq {compare,train,predict,audit}
├── audit.py                отчёт о качестве данных 2021–2026 (можно запускать отдельно)
├── config.py               DataConfig, DecoderConfig, TransformerConfig, TrainingConfig, ExperimentConfig
├── data/
│   ├── models.py           WellSeries (ряды скважины, target, training_mask), Interval
│   ├── readers.py          тестовые файлы: MeasurementsReader, LabelsReader, WellRepository (+ кэш)
│   ├── statistics.py       файлы 2021–2026: MergedStatisticsReader, MonitoringLabelsReader
│   ├── repair.py           BlockShiftRepair (сегменты, сдвиг 0/180), FrequencyCheck
│   └── dataset.py          MergedWellRepository (+ кэш), DataAudit
├── features/builder.py     FeatureBuilder: sequence() для Transformer, tabular() для sklearn
├── models/
│   ├── base.py             EventSegmenter — общий интерфейс: fit / predict_proba / save / load
│   ├── transformer.py      TimeSeriesTransformer (nn.Module), TransformerSegmenter
│   └── classic.py          SklearnSegmenter, classic_models()
├── evaluation/
│   ├── decoding.py         SegmentDecoder: вероятности -> мероприятия
│   ├── metrics.py          EventMatcher, Score
│   ├── experiment.py       CrossValidator, ModelResult
│   └── report.py           ComparisonReport: comparison.xlsx + comparison.png
├── tests/                  pytest на синтетических скважинах
└── weights/                сохранённые модели (после train)
```

Новая модель добавляется наследником `EventSegmenter` и строкой в `model_registry()`
(`models/__init__.py`) — сравнение, отчёт и `predict` подхватят её сами.
