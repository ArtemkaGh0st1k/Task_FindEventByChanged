# ml_freq — ML-детекция ГТМ «увеличение частоты F»

Собственная нейросеть (**Transformer-энкодер для временных рядов, PyTorch**) и
готовые модели **scikit-learn** на одной задаче: по суточным замерам скважины
найти мероприятия «увеличение частоты F» и даты их начала и окончания.

Модуль самостоятельный: своё чтение Excel, свои метрики, от других пакетов
проекта не зависит.

## Быстрый старт

Из корня проекта (`.venv` проекта, зависимости из `req.txt`):

```bash
python -m gtm_detector.ml_freq compare                       # сравнить все модели (~15 мин на CPU)
python -m gtm_detector.ml_freq compare --models gboost extra_trees   # только выбранные
python -m gtm_detector.ml_freq train --model transformer     # обучить на всей разметке, сохранить веса
python -m gtm_detector.ml_freq predict --model transformer   # найти мероприятия без разметки
python -m gtm_detector.ml_freq audit                         # отчёт о качестве данных 2020–2026
python -m pytest gtm_detector/ml_freq/tests                  # тесты
```

Данные по умолчанию (`--dataset merged`) — **14 исходных полугодовых выгрузок**
`resources/statistics/<год>/*.xls` (годы 20–26, 01.01.2020–02.11.2026, 616 скважин)
и разметка технологов `resources/labeled_data.xlsx` (лист «Лист1», 786 строк).
Прежний склеенный файл `.xlsx` тоже читается: передайте его в `--statistics`
(тогда включается исправление сдвигов, см. ниже). Папки `resources/test_datas` в проекте
больше нет, поэтому `--dataset test` без неё не запустится.
Первое чтение 14 файлов `.xls` — около 3 минут, дальше — из кэша (`%TEMP%/gtm_ml_freq_cache`) за доли секунды.

## Данные 2020–2026

### Источник: полугодовые файлы

`HalfYearStatisticsReader` (`data/statistics.py`) читает все `resources/statistics/*/*.xls`:
в каждом листе на параметр строка — скважина, столбцы — даты полугодия. Таблицы периодов
склеиваются на непрерывный календарь (`_join_periods`; пропущенный день — пустая ячейка,
при наложении дат верен более поздний файл).

Особенность формата: библиотека `xlrd` (`xlrd==2.0.2` в `req.txt`) эти `.xls` напрямую
не открывает («size exceeds expected»): выгрузки сохранены не самим Excel, цепочка
секторов потока длиннее размера в каталоге файла. Поэтому поток книги достаёт
`_workbook_stream` (по цепочке секторов, `_chain`), а `xlrd` читает его из памяти.
Сверено с настоящим Excel: 504 случайные ячейки, расхождений 0.

**Сдвига на 180 дней в исходных файлах нет.** Проверка без учёта порога телеметрии:
подъём частоты подтверждается у 427 мероприятий при сдвиге 0 и лишь у 79 при +180.
Поэтому для папки с полугодиями `BlockShiftRepair` не запускается (`MergedWellRepository._repair`
вызывается только для склеенного файла, `statistics.is_file()`), 17 % ячеек больше не
исключается. Для склеенного `.xlsx` исправление остаётся: календарь делится на сегменты —
периоды с одним набором скважин, для каждого проверяются сдвиги 0 и 180 дней (по
эталонной выгрузке `--reference` и по разметке), подтверждённый сдвиг применяется,
противоречивый сегмент исключается.

Мероприятие разметки принимается, только если замеры подтверждают подъём частоты около
даты начала (`FrequencyCheck`). Итог аудита (`audit`, `results/ml_freq/data_audit_halfyear/`):

| Решение                                          | Строк                    |
|--------------------------------------------------|--------------------------|
| **принято (в обучение)**                          | **424** на 369 скважинах |
| частота в замерах не поднялась около даты начала  | 313                      |
| дубликат (та же скважина и дата начала)           | 40                       |
| нет телеметрии частоты у скважины                 | 5                        |
| частота не увеличена (новое ≤ текущего)           | 3                        |
| не выполнено                                      | 1                        |

Принято по годам: 2021 — 48, 2022 — 49, 2023 — 82, 2024 — 59, 2025 — 109, 2026 — 77.
Мероприятий «ПРОДОЛЖАЕТСЯ ЭФФЕКТ» (censored) — 81: конец наблюдения не равен концу эффекта,
дни после него не используются при обучении, ошибка окончания не считается.
Скважины: 369 с разметкой, 242 без разметки, 5 не используются (нет телеметрии частоты).
Раньше (склеенный файл) было 135 мероприятий на 122 скважинах — данных стало в ~3 раза больше.

### Почему 313 строк отброшены

Главная причина — не качество статистики, а **расхождение дат**. Среди 313 отброшенных
в окне ±30 дней вокруг даты технолога подъём частоты ≥ 0,3 Гц есть у 299; у ~250 из них
он виден на **4–30 дней раньше** даты технолога (оценка смещена: в окне могут попадаться
случайные подъёмы, не связанные с мероприятием). Вероятно, технолог ставит начало
мониторинга позже самого подъёма. Критерий `FrequencyCheck` намеренно не менялся:
ослабить его значит учить модель на днях, где частота ещё не менялась. Если эти строки
проверят технологи (`rejected_labels.csv`), каждая исправленная дата — новый пример.

`audit` пишет `results/ml_freq/data_audit_halfyear/data_audit.xlsx` (решение по каждой
строке разметки, статус каждой скважины; лист «сегменты» пуст — исправлять нечего),
`data_audit.png`, `rejected_labels.csv` и `training_data.xlsx`.

## Постановка задачи

Все модели решают одну задачу — **разметку ряда по дням**: для каждого дня
вероятность того, что идёт эффект мероприятия (день между датами начала и
окончания мониторинга в разметке).

Из вероятностей мероприятия получает общий `SegmentDecoder`, одинаково для всех моделей:

1. вероятности сглаживаются скользящим средним за 5 дней;
2. дни с вероятностью > 0.5 — «в эффекте»;
3. разрывы до 3 дней склеиваются, периоды короче 2 дней отбрасываются;
4. начало мероприятия — первый день периода, окончание — последний;
   период, дошедший до конца данных, — «эффект продолжается».

### Почему учимся не на всех днях

В разметке только мероприятия из списка рекомендаций. Реальных подъёмов частоты
в данных больше, и вне разметки «эффекта нет» не значит, что его действительно нет.
Если учить модели на всех днях, они получают противоречивые примеры. Поэтому
обучение идёт только на днях **±45 дней вокруг размеченных мероприятий**
(`WellSeries.training_mask`, `CONTEXT_DAYS` в `config.py`). Это подняло
полноту деревьев с 56 до 69 %.

## Признаки (`features/builder.py`)

15 каналов на каждый день:

| Канал                          | Смысл                                                            |
|--------------------------------|------------------------------------------------------------------|
| `working`                      | скважина работает: F > 10 Гц (в тестовых данных ещё и состояние «раб.»/«нак») |
| `f_rel`, `f_diff`              | частота относительно медианы скважины и её суточное изменение (50- и 150-Гц двигатели сопоставимы) |
| `f_above_min30`, `f_below_max30` | частота относительно минимума / максимума за 30 дней           |
| `liq_vs_30d`, `oil_vs_30d`, `wc_vs_30d`, `pzab_vs_30d` | Qж, Qн, обводнённость, Рзаб относительно прошлых 30 дней |
| `days_since_step`, `step_size` | дней с последнего подъёма частоты и его величина                 |
| `liq_vs_step`, `oil_vs_step`, `wc_vs_step` | Qж, Qн, обводнённость относительно дня перед подъёмом частоты |
| `liq_missing`                  | замера Qж нет                                                    |

Transformer получает эти каналы как последовательность. Моделям scikit-learn
каждый день виден отдельно, поэтому им добавлен контекст: сдвиги каналов на
±1, 3, 7, 14 дней и средние за 7 дней до и после — всего 106 признаков.

## Модели

### Собственная: Transformer для временных рядов (`models/transformer.py`)

```
признаки дня (15) ─► Conv1d, ядро 5 (локальные ступеньки частоты и дебита)
                 ─► + синусоидальное позиционное кодирование
                 ─► 2 × TransformerEncoderLayer (d_model 32, 4 головы внимания, pre-norm)
                 ─► LayerNorm + Linear ─► логит «день внутри эффекта»
```

- ~20 тыс. параметров; модель двунаправленная — детекция офлайн, весь ряд известен.
- Обучение: случайные окна по 128 дней вокруг размеченных мероприятий (аугментация),
  BCE с весом положительного класса, AdamW + косинусное расписание, 80 эпох.
- Крупнее (d_model 64, 3 слоя, ~105 тыс. параметров) — хуже (проверено на 122 скважинах); на таких объёмах
  модель переобучается.

### Готовые модели scikit-learn (`models/classic.py`)

| Имя             | Модель                                            |
|-----------------|---------------------------------------------------|
| `logreg`        | логистическая регрессия (+ стандартизация), линейная база |
| `random_forest` | случайный лес, 300 деревьев                        |
| `extra_trees`   | Extra Trees, 300 деревьев                          |
| `gboost`        | градиентный бустинг `HistGradientBoostingClassifier` |

У всех — веса классов «balanced» (дней эффекта меньше).

## Как оценивается (`evaluation/`)

- **Перекрёстная проверка по скважинам, 5 фолдов** (`CrossValidator`): модель не
  видит скважины, на которых её проверяют; разбиения одинаковы для всех моделей.
- **Сопоставление** (`EventMatcher`): найденное и размеченное мероприятие — одно и
  то же, если даты начала отличаются не больше чем на 7 дней; один-к-одному,
  сначала ближайшие пары.
- **Метрики** (`Score`): доля найденных размеченных мероприятий (recall), точность
  (precision), F1, точность дат начала и окончания (точно / ±1 / ±3 / ±7 дней),
  ROC-AUC по дням — качество вероятностей до декодирования.

Точность (precision) по этой разметке занижена: в ней не все реальные подъёмы
частоты, поэтому найденное «вне разметки» — не обязательно ошибка.

Выводы:

- **Лучшие ML-модели — деревья.** На данных 2020–2026 градиентный бустинг находит 74 %
  размеченных мероприятий, начало точно в день — 36 %, ±3 дня — 89 %; Extra Trees и

  лучше всех ставит конец (±7 дней — 70 %).
- **Собственный Transformer слабее деревьев** (полнота 46 %, ROC-AUC 0,75) даже на 424
  мероприятиях; он уступает и логистической регрессии по полноте. Данных всё ещё мало:
  ~300 скважин в обучающем фолде. Нейросеть с вниманием выигрывает
  на тысячах примеров; здесь деревья с явно заданным контекстом (сдвиги ±14 дней)
  эффективнее. Увеличение модели (d_model 64, 3 слоя) и обучения (80 эпох) не
  помогло: полнота осталась ~50 %.
- **Все ML-модели пока уступают правилам**, особенно по точной дате окончания.
  Правила напрямую кодируют то, как технологи закрывают эффект; модели должны
  выучить это из нескольких сотен примеров.
- **Что даст рост:** согласованные даты. 313 из 786 строк отброшены, потому что подъём
  частоты в замерах виден на 4–30 дней раньше даты технолога (см. «Почему 313 строк
  отброшены»): если технологи уточнят даты или подтвердят, что начало мониторинга
  ставится позже подъёма, обучающих примеров станет ещё больше. Transformer стоит
  прогнать на нескольких зёрнах случайности, прежде чем делать вывод о нём.
