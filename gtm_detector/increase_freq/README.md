# increase_freq — детекция ГТМ «увеличение частоты F» по правилам

По суточным замерам скважин (частота ЭЦН, дебиты, обводнённость, состояние)
определяет, было ли на скважине мероприятие **«увеличение частоты F»**, и если
было — даты его **начала и окончания**.

Пока есть размеченные технологами мероприятия, параметры алгоритма подбираются
по ним. Потом подобранные параметры используются без разметки.

Это третий подход в проекте (после `prompt-engineering` и `neural-network`):
последовательность объяснимых правил, пороги которых подбираются по разметке.

## Быстрый старт

Все команды — из **корня проекта** (`Task_FindEventByChanged/`), окружение — общее
для проекта (`.venv`, зависимости из `req.txt`: numpy, pandas, openpyxl; matplotlib — для графиков).

```bash
.venv/Scripts/activate
```

Короче всего — через корневой `main.py`. Без аргументов это полный прогон:
поиск, сравнение с разметкой, сводка качества и графики скважин (~1–2 мин):

```bash
python main.py
python main.py calibrate --cv 5
```

`main.py` принимает те же команды и параметры, что и
`python -m gtm_detector.increase_freq`.

Поиск мероприятий (разметка не нужна):

```bash
python -m gtm_detector.increase_freq detect
```

Со сравнением с расставленными датами и графиками:

```bash
python -m gtm_detector.increase_freq detect --results resources/output_dataset.xlsm --plots
```

Подбор параметров по разметке (перезаписывает `gtm_detector/increase_freq/params.json`):

```bash
python -m gtm_detector.increase_freq calibrate --cv 5
```

Параметры команды `detect`:

| Параметр         | Что делает                                                                 |
|------------------|----------------------------------------------------------------------------|
| `--measurements` | файл замеров (по умолчанию `resources/input_dataset.xlsx`)                 |
| `--results`      | файл с разметкой — для сравнения и сводки (по умолчанию не используется)   |
| `--params`       | параметры детектора (по умолчанию `gtm_detector/increase_freq/params.json`)|
| `--out-dir`      | папка прогона (по умолчанию `results/increase_freq/<дата_время>/`)         |
| `--plots`        | построить сводку и графики скважин                                         |
| `--all-wells`    | с `--plots`: рисовать и скважины без разметки (`wells/нет_в_разметке`)     |
| `--workers`      | с `--plots`: число процессов отрисовки (по умолчанию до 4)                 |

Пути по умолчанию заданы в `constants/path.py`
(`Constant.INPUT_DATASET`, `Constant.OUTPUT_DATASET`, `Constant.INCREASE_FREQ_PARAMS`,
`Constant.INCREASE_FREQ_RESULTS_DIR`).

Из Python:

```python
from constants.path import Constant
from gtm_detector.increase_freq import DetectorConfig, FrequencyIncreaseDetector
from gtm_detector.increase_freq.excel import MeasurementsReader

wells = MeasurementsReader(Constant.INPUT_DATASET).read()
detector = FrequencyIncreaseDetector(DetectorConfig.load(Constant.INCREASE_FREQ_PARAMS))
for event in detector.detect(wells[0]):
    print(event.date_step, event.start, event.end, event.end_reason_title)
```

## Входные и выходные данные

### Замеры — `resources/input_dataset.xlsx`

Лист на параметр, строка — скважина, столбцы `ДД.ММ.ГГГГ` — суточные значения.

| Лист      | Параметр                     | Поле в коде     |
|-----------|------------------------------|-----------------|
| `Qж`      | дебит жидкости               | `debit_liquid`  |
| `Обв`     | обводнённость, %             | `watercut`      |
| `Qн`      | дебит нефти                  | `debit_oil`     |
| `Fэцн ТМ` | частота насоса, Гц           | `frequency`     |
| `Рзаб`    | забойное давление            | `pressure_zab`  |
| `Pлин`    | линейное давление            | `pressure_line` |
| `Прим`    | состояние скважины по дням   | `state`         |

Состояния `раб.` и `нак` (работа в накоплении) — скважина работает; `ост.`,
`б/д тг`, `б/д пр л`, `пьез`, `конс`, `набл` — не работает.

Номера скважин на месторождении повторяются, поэтому скважина определяется
парой **(номер, куст)**.

Можно подавать данные и словарём (исходный формат постановки) —
см. `Well.from_dict`:

```python
{
    "well_id": "124",
    "date": [...],
    "frequency": [...],
    "state": [...],
    "debit_liquid": [...],
    "debit_oil": [...],
    "watercut": [...],
    "pressue_zab": [...],
    "pressure_lineqr": [...],
}
```

### Разметка — лист `Результат__*` файла `resources/output_dataset.xlsm`

В разметку попадают строки, где:

- «Наименование мероприятия» = **Увеличение F**;
- «Успешно/не успешно» = **да**;
- заполнены «дата начала мониторинга» и «дата окончания мониторинга».

Опечатки в датах (`21.04.2026г`, `08.02.206`) разбираются автоматически.
Остальные мероприятия с частотой из этого листа (неуспешные, без дат)
используются как «известные»: срабатывание детектора рядом с ними не считается
ложным.

### Результат — папка `results/increase_freq/<дата_время>/`

```
events.xlsx          найденные мероприятия
summary.png          сводка качества (если передана разметка и --plots)
wells/
├── совпало/         все метки найдены: начало ±1 дн, окончание ±3 дн
├── ошибка_дат/      все метки найдены, но даты расходятся сильнее
├── пропущено/       хотя бы одна метка не найдена

```

`events.xlsx`:

- **Мероприятия** — все найденные мероприятия: скважина, куст, день скачка
  частоты, начало и окончание эффекта, причина окончания, F до/после,
  Qж/Qн/обводнённость до и в начале эффекта, уверенность.
- **Сравнение с разметкой** — по каждому размеченному мероприятию: даты

Панели с общей осью дат: **F**, **Qж**, **Qн**, **обводнённость** и полоса

| Обозначение                 | Смысл                                                           |
|-----------------------------|-----------------------------------------------------------------|
| синяя заливка               | период эффекта, найденный детектором                            |
| синяя линия                 | найденный скачок частоты                                        |
| синий пунктир на Qж и Qн    | уровень «до»: по возврату Qн к нему детектор закрывает эффект   |
| оранжевая штриховка         | период мониторинга из разметки                                  |
| оранжевый штрих             | «Дата выполнения» из разметки                                   |
| серые полосы внизу          | дни, когда скважина не работала                                 |

Под заголовком — по каждой метке: период по разметке, найденный период,

Скважины разложены по статусам, поэтому разбор ошибок удобно начинать с
папок `пропущено/` и `ошибка_дат/`.

### Сводка — `summary.png`

Одна страница из шести панелей:

1. ошибка даты начала (найдено − разметка), гистограмма по дням;
2. то же для окончания;
3. окончание: разметка против найденного — точки на диагонали = точное попадание;
4. доля окончаний с ошибкой ≤ 3 дн по причине окончания в разметке
   (по обводнённости / по жидкости / остановка / отказ ЭЦН);
5. мероприятия по месяцам: совпавшие с разметкой, вне разметки, пропущенные;
6. ключевые метрики.

Цвета: синий — найденное детектором, оранжевый — разметка, серый — замеры и
второстепенное. Пара синий/оранжевый различима и при нарушениях цветового зрения.

## Подход

Анализ разметки показал, что даты технологов означают следующее:

| Дата в разметке             | Что это по данным                                                          |
|-----------------------------|----------------------------------------------------------------------------|
| Дата выполнения мероприятия | день скачка частоты в замерах                                              |
| Дата начала мониторинга     | первый день, когда Qж или Qн стали выше, чем до подъёма (обычно +1–5 дней) |
| Дата окончания мониторинга  | день перед тем, как эффект пропал: Qн вернулся к уровню «до» или скважину остановили |

Поэтому алгоритм — это последовательность правил, а не «чёрный ящик».
Каждое правило объяснимо, а его пороги подбираются по разметке.

```
 суточные замеры скважины
          │
          ▼
 ┌──────────────────────┐   рабочие дни, медианное сглаживание,
 │ 1. Скачок частоты    │   ступени ≥ min_step, объединение ступеней,
 │    StepDetector      │   проверка удержания нового уровня
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐
 │ 2. Базовый режим     │   Qж, Qн, обводнённость в последний
 │    baseline_before   │   рабочий день перед скачком
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐   первый рост Qж/Qн выше базы
 │ 3. Начало эффекта    │   (или первый новый замер);
 │    EffectStartFinder │   нет роста добычи — нет мероприятия
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐   Qн ≤ базы N дней подряд,
 │ 4. Окончание эффекта │   или остановка скважины;
 │    EffectEndFinder   │   иначе «эффект продолжается»
 └──────────┬───────────┘
            ▼
       Event(date_step, start, end, end_reason, ...)
```

### Шаг 1. Скачок частоты — `StepDetector`

1. Оставляются только рабочие дни: `state=True` и частота > `min_working_freq`.
   Поэтому пуск после простоя (0 → 50 Гц) не считается подъёмом.
2. Частота сглаживается скользящей медианой (`smooth_window`): одиночные
   выбросы и ошибки ввода пропадают, а ступенька остаётся на своём месте.
3. День с приростом ≥ `min_step` Гц — ступень. Ступени с разрывом не больше
   `max_gap` рабочих дней и без снижения между ними объединяются: ступенчатый
   вывод 45 → 46 → 47 → 48 Гц за несколько дней — одно мероприятие.
4. Скачок принимается, если суммарный прирост ≥ `min_total` и новый уровень
   держится `hold_days` дней (не всплеск с возвратом). Скачки сразу после
   простоя можно отбросить (`skip_after_restart`).

### Шаг 2. Базовый режим — `baseline_before`

Qж, Qн и обводнённость в последний рабочий день перед скачком. С ними
сравнивается всё дальнейшее.

### Шаг 3. Начало эффекта — `EffectStartFinder`

- `start_mode="rise"`: первый день после скачка, когда Qж или Qн выше базовых;
- `start_mode="change"`: первый день, когда пришёл новый замер Qж/обводнённости.

Если за `start_max_days` признака нет — начало = скачок + `start_default` дней.
Если в первые `response_days` дней добыча не выросла (`require_response`) —
подъём частоты не дал эффекта, мероприятие не засчитывается (в разметке только
успешные).

### Шаг 4. Окончание эффекта — `EffectEndFinder`

Окончание — день перед первым из событий:

- **остановка** скважины на `stop_days` дней подряд;
- **потеря эффекта** по правилам `end_rules`:
  `oil` — Qн ≤ базового; `liq` — Qж ≤ базового; `wc` — обводнённость выше базовой
  (каждое с допуском `*_tolerance`).

Потеря эффекта должна держаться `end_confirm_days` рабочих дней подряд —
разовое колебание замера не закрывает мероприятие. Первые `min_effect_days`
дней после начала не проверяются. Если до конца данных ничего не случилось —
`end=None`, «эффект продолжается».


Принципы:

- **Данные отделены от алгоритма.** `excel/` превращает файлы технологов в
  объекты `Well`; алгоритм работает только с `Well` и ничего не знает об Excel.
  Другой источник данных (БД, CSV, словари) — это новый reader.
- **Один шаг — один класс.** Каждый шаг алгоритма можно проверить и заменить
  отдельно; `FrequencyIncreaseDetector` только связывает их.
- **Все параметры — в `DetectorConfig`.** Неизменяемый dataclass, сохраняется
  в JSON и загружается из него (`save` / `load`). Режимы — перечисления
  `StartMode`, `EndRule`, `EndReason`, а не «магические строки».
- **Оценка отделена от детекции.** `EventMatcher` и `Score` не зависят от
  алгоритма — ими можно сравнить с разметкой любую будущую модель.

## Подбор параметров и оценка качества

**Сопоставление** (`EventMatcher`): найденное мероприятие и размеченное — одно и
то же, если даты начала отличаются не более чем на 7 дней **или** скачок частоты
не дальше 3 дней от «Даты выполнения». Начало мониторинга иногда ставят через
2–10 недель после выполнения — второе условие нужно для таких случаев.
Сопоставление один-к-одному, сначала самые близкие пары.

**Метрики** (`Score`): полнота (recall), точность (precision), F1; для дат —
средняя ошибка в днях и доли точных попаданий / в пределах ±1, ±3, ±7 дней.

**Подбор** (`Calibrator`): покоординатный спуск по сетке значений
(`DEFAULT_SEARCH_SPACE`). По очереди перебирается каждый параметр, изменение
принимается, если растёт целевая функция:

```
цель = F2 − 0.01 · (ошибка начала + 0.5 · ошибка окончания)
```

- **F2**, а не F1: полнота важнее точности. В разметке есть только
  мероприятия из списка рекомендаций (и только до июня), а реальных подъёмов
  частоты в данных больше. Если гнаться за точностью, подбор начнёт «душить»
  настоящие события.
- Ошибка дат **обрезается на 14 днях**: пара грубых промахов не должна
  перевешивать долю точных попаданий.

**Кросс-валидация** (`Calibrator.cross_validate`): скважины делятся на 5 частей,
подбор идёт на четырёх, проверка — на пятой. Это честная оценка качества на
новых скважинах.

## Результаты

Данные: 516 скважин, 01.01–31.08.2026. Разметка: 117 мероприятий на 105 скважинах.

| Метрика                               | Кросс-валидация | Подбор на всей разметке |
|---------------------------------------|-----------------|-------------------------|
| Найдено размеченных мероприятий       | 89 %            | 97 %                    |
| Начало: точно / ±1 день / ±3 дня      | 78 / 85 / 90 %  | 81 / 88 / 91 %          |
| Окончание: точно / ±3 / ±7 дней       | 68 / 73 / 77 %  | 70 / 74 / 79 %          |
| Скачок F vs «Дата выполнения»: точно / ±2 | 65 / 78 %   | 65 / 79 %               |

Подобранные правила (`params.json`): начало — первый рост Qж/Qн выше базы;
окончание — Qн ≤ базового 3 рабочих дня подряд или остановка на 2+ дня.

По всему файлу найдено 832 мероприятия на 328 скважинах.

## Ограничения и развитие

- **Точность (precision) по разметке не измерить.** Около 2/3 найденных
  мероприятий нет в разметке, но почти все они — реальные подъёмы частоты
  (медиана +1 Гц), не вошедшие в список рекомендаций. Для оценки нужна ручная
  проверка выборки найденных событий.
- **Окончание — самое неустойчивое.** Технологи закрывают эффект по-разному
  (то по снижению дебита на 1 м³, то не реагируют на скачок обводнённости);
  ошибки бывают до 1–3 месяцев. Улучшить можно, уточнив у технологов правило
  закрытия эффекта.
- Повторный подъём частоты во время действующего эффекта — отдельное
  мероприятие; их периоды могут перекрываться.
- Следующий шаг, если правил не хватит: детектор как генератор кандидатов +
  классификатор (например, градиентный бустинг) по признакам вокруг скачка,
  обученный на разметке.


Каждый прогон создаёт новую папку `results/increase_freq/<дата_время>/` — старые
прогоны не перезаписываются, лишние можно удалять вручную.
