Claude Code читает этот файл в начале каждой сессии и передаёт его агентам из

## Задача

Поиск геолого-технических мероприятий (ГТМ) на нефтяных скважинах по суточным
замерам. Главное мероприятие — **«увеличение частоты F»** (подъём частоты двигателя
ЭЦН): найти мероприятие и даты **начала** и **окончания** эффекта так, как их ставят
технологи.

Рабочая ветка машинного обучения — `feature/create-llm-model`. В ветке
`feature/increase-f-gtm` лежит детектор на правилах. Это **опорный уровень, который
модели пока не превзошли** (найдено 89 %, дата начала точно — 78 %). Любое улучшение
сравнивается и с ним.

Подробное описание архитектуры, признаков и результатов —
`gtm_detector/ml_freq/README.md`. Прочитай его перед любой работой в `ml_freq`.

Основные классы `ml_freq`:

- `data.WellSeries` — скважина: таблица `frame` (дни × `SERIES_COLUMNS`), разметка
  `labels: list[Interval]`, методы `target()` и `training_mask(context_days)`.
- `features.FeatureBuilder` — `sequence()` (15 каналов для Transformer) и `tabular()`
  (106 признаков для scikit-learn). Порядок `SEQUENCE_CHANNELS` сохраняется в весах `.pt`.
- `models.EventSegmenter` — общий интерфейс моделей: `fit`, `predict_proba`, `save`, `load`.
  Новая модель — это наследник класса и строка в `model_registry()` (`models/__init__.py`).
- `evaluation.SegmentDecoder` — превращает вероятности в интервалы, одинаково для всех моделей.
- `evaluation.CrossValidator` — перекрёстная проверка **по скважинам**; `EventMatcher`
  сопоставляет мероприятия (допуск ±7 дней), `Score` считает метрики.
- `config.py` — все гиперпараметры в неизменяемых dataclass-классах. Чисел, вписанных
  прямо в код, нет.

## Команды

Окружение: Windows, Python 3.12, виртуальное окружение `.venv` в корне. Запускать из
корня проекта.

```bash
.venv/Scripts/python -m pytest gtm_detector/ml_freq/tests -q          # тесты (секунды)
.venv/Scripts/ruff check gtm_detector                                # проверка PEP 8
.venv/Scripts/ruff format --check gtm_detector                       # проверка форматирования
.venv/Scripts/python -m gtm_detector.ml_freq compare --models gboost extra_trees   # около 2 мин
.venv/Scripts/python -m gtm_detector.ml_freq compare                 # все модели, около 15 мин на процессоре
.venv/Scripts/python -m gtm_detector.ml_freq compare --models transformer --epochs 20  # быстрая проверка
.venv/Scripts/python -m gtm_detector.ml_freq audit                   # аудит данных 2021–2026
.venv/Scripts/python -X utf8 docs/ml_freq_walkthrough/build.py --check   # какие пояснения к PDF устарели
.venv/Scripts/python -X utf8 docs/ml_freq_walkthrough/build.py           # собрать PDF-разбор (около минуты)
```

После каждого ответа, в котором менялись файлы проекта, Stop-хук `.claude/hooks/docs_sync.py`
просит вызвать агента `docs-maintainer`: он обновляет README, пояснения и PDF-разбор и
предлагает описание коммита. Агент не видит переписку — в задаче для него кратко перечисли,
что и зачем изменилось.

Долгие команды (`compare` для всех моделей, `train --model transformer`) запускай в фоне.
Первое чтение Excel занимает около 30 секунд, дальше данные берутся из кэша
`%TEMP%/gtm_ml_freq_cache`. Если менялись `data/readers.py`, `data/statistics.py`,
`data/repair.py` или `data/dataset.py`, кэш может быть устаревшим: проверь ключ кэша
или удали папку кэша.

## Стиль кода

- **PEP 8**, проверяется `ruff` (настройки в `pyproject.toml`, длина строки — 99 символов).
  В старом коде есть строки длиннее — исправляй только те строки, которые и так меняешь;
  **не переформатируй файлы целиком** без просьбы, это раздувает изменения.
- `from __future__ import annotations`, аннотации типов у всех публичных функций,
  `X | None` вместо `Optional[X]`, `collections.abc` для `Sequence`, `Mapping`, `Callable`.
- Импорты внутри пакета — относительные (`from ..data import WellSeries`).
- Строки документации и комментарии — **на русском**, коротко, объясняют *почему*.
  Имена в коде — на английском, в стиле `snake_case` и `PascalCase`.
- Настройки — неизменяемые dataclass-классы (`frozen=True`) в `config.py`; новый
  гиперпараметр добавляется туда со значением по умолчанию и комментарием, почему оно такое.
- В коде библиотеки — `logging`, а не `print`; `print` допустим только в `cli.py`.
- Пути — через `pathlib.Path`. Имена файлов с кириллицей и латинской «c»
  (`Итоговый_файл_c_2021_2026.xlsx`) копировать из `config.py`, а не набирать вручную.

## Правила машинного обучения (обязательные)

1. **Никакой утечки между скважинами.** Разбиение только по скважинам
   (`CrossValidator.folds`). Нормировки и статистики считаются внутри скважины или по
   обучающим скважинам фолда.
2. **Признаки — только из `FeatureBuilder`.** Добавил канал — обнови `SEQUENCE_CHANNELS`,
   тесты и README; старые веса `.pt` станут несовместимы (это проверяется в `load`).
3. **Обучение только на днях из `training_mask`** (±`CONTEXT_DAYS` вокруг размеченных
   мероприятий). Дни после мероприятий «ПРОДОЛЖАЕТСЯ ЭФФЕКТ» (`censored`) в функцию
   потерь не входят.
4. **Воспроизводимость:** зерно случайности из настроек передаётся в `torch.manual_seed`,
   `np.random.default_rng` и `random_state` моделей scikit-learn. Глобальный `np.random.*`
   не использовать.
5. **Честное сравнение:** одинаковые фолды, один `SegmentDecoder`, метрики из `Score`.
   Говорить «стало лучше» можно только с таблицей до и после из `compare`, а для
   Transformer — по нескольким зёрнам случайности (разброс между ними сравним с эффектом).
6. Точность (precision) занижена намеренно: разметка неполная. Главные метрики — полнота
   (доля найденных мероприятий), точность даты начала ±1 и ±3 дня, окончания ±3 и ±7 дней,
   ROC-AUC по дням.
